1. Réflexions technologiques initiales

L'énoncé impose une base relationnelle et une base non relationnelle et laisse le reste libre. Mes critères : pouvoir expliquer chaque ligne devant le jury, couvrir toutes les compétences du titre (front, back, SQL, NoSQL, déploiement), et produire une application légère, sécurisée et accessible.

3. Architecture

Architecture MVC légère. Seul le dossier public/ est exposé par le serveur web : le code, les vues et le fichier .env ne sont jamais téléchargeables.

public/index.php      point d'entrée unique : configuration, en-têtes de sécurité, session, déclaration des routes
src/Core/             Router (CSRF + rôles), Auth (sessions), Csrf, Validator, Security, Database (PDO), Mongo, View, Flash
src/Controllers/      Page, Auth, Contact, Galerie, Espace (joueur), Gestion (employé), Admin
src/Models/           Utilisateur, Personnage, Accessoire, Avis, TentativeConnexion (MySQL), MessageContact (MongoDB)
src/Services/         Apparence (options + rendu SVG), ActivityLog (MongoDB), MailService, MotDePasse
templates/            gabarit commun et vues
database/             01_schema.sql (création), 02_donnees.sql (données de démonstration)
tests/                tests PHPUnit

4. Modèle conceptuel de données

erDiagram UTILISATEURS ||--o{ PERSONNAGES : "crée" UTILISATEURS ||--o{ AVIS : "rédige" PERSONNAGES ||--o{ AVIS : "reçoit" PERSONNAGES ||--o{ PERSONNAGE_ACCESSOIRES : "porte" ACCESSOIRES ||--o{ PERSONNAGE_ACCESSOIRES : "équipe" UTILISATEURS { int id PK varchar email UK varchar pseudo UK varchar mot_de_passe "argon2id" enum role "joueur, employe, admin" enum statut "actif, suspendu" bool doit_changer_mdp } PERSONNAGES { int id PK int utilisateur_id FK varchar nom UK enum genre enum forme_visage enum forme_yeux enum forme_nez enum forme_bouche enum coiffure char couleur_peau char couleur_cheveux char couleur_yeux enum statut "en_attente, valide" bool partage datetime cree_le } ACCESSOIRES { int id PK varchar nom UK enum categorie "vetement, armure, arme, accessoire" varchar visuel char couleur bool actif } PERSONNAGE_ACCESSOIRES { int personnage_id PK,FK int accessoire_id PK,FK enum categorie "UNIQUE avec personnage_id" } AVIS { int id PK int personnage_id FK int utilisateur_id FK tinyint note "CHECK 1 à 5" varchar commentaire enum statut "en_attente, valide, refuse" }

Règles de gestion traduites dans le schéma

  • E-mail, pseudo, nom de personnage et nom d'article uniques : contraintes UNIQUE.
  • Un seul article par catégorie sur un personnage : UNIQUE (personnage_id, categorie) dans la table d'association.
  • Un seul avis par joueur et par personnage : UNIQUE (personnage_id, utilisateur_id) ; note de 1 à 5 : CHECK.
  • Un personnage ne peut être partagé que s'il est validé : CHECK (partage = FALSE OR statut = 'valide').
  • Supprimer un compte supprime ses personnages, leur équipement et les avis (ON DELETE CASCADE).
  • Traits physiques en ENUM : la base refuse toute valeur hors liste, en plus du contrôle PHP.
  • Le compte administrateur est créé par le script SQL : aucune fonctionnalité ne permet d'en créer un.

7. Sécurité (résumé)

RisqueProtection
Injection SQLPDO, requêtes préparées, EMULATE_PREPARES = false, noms de colonnes jamais issus de la saisie
Injection NoSQLFiltres MongoDB construits avec des valeurs typées (chaînes), expressions régulières échappées
XSSÉchappement systématique (e()), SVG construit à partir de listes fermées, CSP sans script en ligne
CSRFJeton vérifié par le routeur pour toute requête POST, cookie SameSite=Lax
Mots de passeRègles CNIL, hash argon2id, mot de passe provisoire aléatoire (random_int) à changer obligatoirement
Force brute5 échecs par e-mail ou 20 par IP en 15 minutes
SessionsCookie HttpOnly / Secure, régénération à la connexion, expiration, compte suspendu déconnecté immédiatement
Contrôle d'accèsRôle exigé déclaré sur chaque route ; un joueur n'agit que sur ses personnages ; rôle imposé dans les requêtes de suspension
Données invalidesValidation serveur de chaque champ, refus des requêtes non UTF-8 (400)
Fuite d'informationsErreurs masquées en production, version d'Apache/PHP masquée, messages neutres (connexion, mot de passe oublié)

8. Déploiement

Démarche. L'application a besoin de PHP 8.3 avec l'extension MongoDB, d'une base MySQL, d'une base MongoDB et d'un serveur SMTP, le tout en HTTPS. J'ai retenu alwaysdata (hébergeur français : PHP, MySQL, SMTP, SSH et certificat Let's Encrypt, offre gratuite de 100 Mo) et MongoDB Atlas (offre gratuite M0, hébergée en Europe). Heroku et fly.io, cités dans l'énoncé, demandent une carte bancaire ou une image Docker à maintenir ; Vercel ne fait pas tourner PHP nativement.

Étapes

  1. MongoDB Atlas : créer un cluster M0 (région Europe), un utilisateur limité au rôle readWrite sur la base fantasyrealm, autoriser l'IP du serveur, copier la chaîne mongodb+srv://….
  2. alwaysdata : créer le compte, choisir PHP 8.3, vérifier l'extension mongodb (sinon pecl install mongodb), créer la base MySQL et son utilisateur, créer le site avec pour racine le dossier public/, activer HTTPS et la redirection.
  3. Code (en SSH) : 
    git clone https://github.com/<compte>/fantasyrealm.git
cd fantasyrealm
composer install --no-dev --optimize-autoloader
cp .env.example .env && nano .env      # APP_ENV=prod, accès MySQL, MongoDB, SMTP
chmod 600 .env
  4. Base de données : importer database/01_schema.sql puis database/02_donnees.sql (données de démonstration utiles au jury) avec phpMyAdmin ou mysql -h … -u … -p base < database/01_schema.sql.
  5. Vérifications : HTTPS actif, /.env et /src/ inaccessibles (404), en-têtes de sécurité présents (curl -I), parcours complet avec les comptes de test, e-mails reçus, logs visibles dans l'administration.
  6. Mises à jour : fusion dans main, puis git pull et composer install --no-dev sur le serveur.

Mise en ligne réalisée

Application en production : https://kiwimandjaro07.alwaysdata.net (code : https://github.com/kiwimandjaro07/fantasyrealm).

Difficultés rencontrées et solutions :

  • Extension PHP MongoDB absente sur l'hébergement : compilée avec l'outil d'alwaysdata ad_install_pecl mongodb, puis déclarée dans le php.ini (menu Environnement) : extension=/home/kiwimandjaro07/php-ext/mongodb-8.3.so.
  • Accès refusé à MySQL (erreur 1044) : alwaysdata préfixe automatiquement le nom des bases ; la base s'appelle kiwimandjaro07__fantasyrealm. Vérification avec SHOW DATABASES;.
  • Accès réseau à MongoDB Atlas : l'offre gratuite d'alwaysdata n'ayant pas d'adresse IP sortante fixe, la liste d'accès d'Atlas autorise 0.0.0.0/0 ; la base reste protégée par un utilisateur dédié et un mot de passe, et la connexion est chiffrée (TLS).
  • Fichier .env mal rempli : une valeur contenant des espaces faisait échouer la lecture de la configuration, et le message d'erreur affichait des chemins du serveur. Correction du code : les erreurs ne sont plus jamais affichées avant la lecture de la configuration, et une configuration invalide renvoie une page neutre.
  • HTTPS : redirection automatique de HTTP vers HTTPS ajoutée dans l'application, en plus de l'en-tête HSTS.

Vérifications effectuées après la mise en ligne : pages publiques en 200, fichiers .env, composer.json et vendor/ inaccessibles (404), en-têtes de sécurité présents, cookie de session Secure; HttpOnly; SameSite=Lax, connexion d'un joueur, requête sans jeton CSRF refusée (403), accès à l'espace employé par un joueur refusé (403).
